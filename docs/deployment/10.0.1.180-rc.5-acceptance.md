## 执行和结果

执行同一发布包内的安装器：

```bash
bash /data/sudostack-ci/38353239849/assets/install-atlas.sh \
  --host 10.0.1.180 --root /data/atlas --add-router
```

随后重复执行同一命令，再执行：

```bash
/data/atlas/restart.sh
python3 /data/atlas/smoke.py --root /data/atlas --resume
/data/atlas/verify.sh
```

- SudoRouter 和原有五个 Deployment 均为 1/1 Ready，全部使用固定 digest 镜像。
- 增补只新增 Router 并更新网关以开放 9443；Moss、Nexus、SudoWork 和 PostgreSQL 的原 Pod UID 保留。原管理员凭据及 Vault 主密钥保持不变。
- 相同版本重复安装保留全部六个 Pod UID，以及管理员、Vault 和 Router 凭据。
- 业务重启后六个 Pod 全部重新创建；同一会话经真实 SudoRouter 和临时 Anthropic 上游完成回复、WebSocket、gVisor 及历史恢复，所有持久凭据保持不变。
- 从开发机信任安装 CA 后，9443 页面、版本状态、管理员登录和模型令牌访问均通过。Moss 的模型令牌不能调用 Router 管理 API。
- Moss 的内部模型地址为 `http://sudorouter.atlas-system.svc.cluster.local:3000/v1`，模型调用令牌已通过 Moss 配置 API 存入 Nexus。
- 临时渠道和测试资源清除，Router 剩余上游渠道数为 0。当前尚未配置真实模型渠道或验证真实模型效果。

## 验收中修复的问题

rc24 的内存渠道缓存不会在创建渠道时立即刷新，导致刚添加的渠道无法使用。此单节点 SQLite 配置关闭内存渠道缓存，直接读取数据库；[对照结果](evidence/10.0.1.180-rc.4/router-cache-regression.json) 验证了失败和修正后的实际会话。

新建模拟上游的 Pod Ready 早于 Service 转发规则生效，会出现 `connection refused` 并由 Router 返回 HTTP 500。验收现在先从 Router Pod 检查该 Service 的 `/healthz`，确认连通后才发起模型请求。[回归结果](evidence/10.0.1.180-rc.5/router-readiness-regression.json) 覆盖独立数据库、两次重启和每次新建 Service。rc.3/rc.4 未通过 CI 发布门槛，未创建 Release。
